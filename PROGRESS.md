## 5. Environment notes

- JDK 21 at `/usr/lib/jvm/java-21-openjdk-amd64`, JDK 25 at `/usr/lib/jvm/java-25-openjdk-amd64`. The default `java` on PATH is 25, so set `JAVA_HOME` explicitly for every build.
- `mvnw` is committed without the executable bit (`core.fileMode=false`), so run it as `sh mvnw`.
- The Docker daemon does not autostart (no systemd in this WSL session). `service docker start` fails with `ulimit: error setting limit (Invalid argument)` because the shell's soft fd limit (1048576) is above the hard limit the init script sets (524288). Start it with `bash -c 'ulimit -Sn 1024; service docker start'`.
- Docker Engine 29.x is available locally; Testcontainers needs it. Engine 29 rejects Docker API clients older than 1.44, so Testcontainers below 1.21.4 fails with "client version 1.32 is too old". Phase 0 overrode `testcontainers.version` to 1.21.4 for that reason; Boot 3.5.16 manages 1.21.4 itself, so Phase 1 removed the override. In Phase 2, Boot 4 brings Testcontainers 2.x: the artifact becomes `testcontainers-postgresql` and `PostgreSQLContainer` moves to `org.testcontainers.postgresql`.
- The VS Code Java extension rebuilds into `target/` when `pom.xml` changes, which can make `mvn clean` fail with "Failed to delete .../target". Rerunning the command fixes it.
- The three `@SpringBootTest` classes use identical annotations so they share one cached context and one container. Keep it that way when adding integration tests.

## 6. Noticed, not fixed

- `mvnw` lacks the executable bit in git (the Dockerfile works around it with `chmod`).
- `GlobalExceptionHandler`'s catch-all `@ExceptionHandler(Exception.class)` also catches Spring's `NoResourceFoundException`, so every unknown URL returns 500 (logged at ERROR) instead of 404. This predates the upgrade.
- README's "Run with coverage" command (`jacoco:report`) does not work: no JaCoCo plugin is configured in `pom.xml`.
- Fixed in Phase A: `adjustStock` and `reserveStock` used to return a stale `availableQuantity`; over-reserving used to return 400 instead of 409.
- `processShipment` reserves from the lowest-id inventory row for the item in that warehouse, whatever its zone. If that row is short but another zone has stock, the reservation fails with 409. Phase D's allocation replaces this.
- Fixed in Phase C: cancelling a PROCESSING outbound shipment now releases its reservation, and SHIPPED now removes the stock.
- `PUT /api/v1/inventory/{id}` does not take a row lock; a concurrent change is caught by `@Version` and returns 409. It can also still try to set `reservedQuantity` above `quantity`, which the CHECK rejects with the generic 409 "The request conflicts with existing data." rather than a specific message.
- The `DataIntegrityViolationException` handler is global, so other constraint violations that used to return 500 (for example a duplicate shipment `trackingNumber`, or a second inventory row for the same item, warehouse and zone) now return 409 too.
- `DELETE /api/v1/inventory/{id}` still deletes a row that has reserved stock.
- No lock timeout is set, so a request waits as long as another transaction holds the inventory or shipment row lock.
- Fixed in Phase C: inventory is unique on (item, warehouse, zone, location) with NULLS NOT DISTINCT.
- `inventory.location_id` is mapped as a plain `Long` in `Inventory` (not a relation, to keep ModelMapper from seeing a second `warehouse.id`) but is not in `InventoryDTO`, so the `inventory.json` baseline is unchanged; `inventory.lpn_id` is not mapped. LPNs have no entity or endpoints.
- `DELETE /api/v1/zones/{id}` now returns 409 for any zone that has locations, which includes every seeded zone (consequence of RESTRICT on `locations.zone_id`).
- An invalid enum in a query or path parameter (for example `GET /api/v1/locations?type=SHELF`, or the existing `/api/v1/zones/type/{type}`) falls through to the catch-all handler and returns 500 instead of 400.
- A duplicate location code returns the generic 409 message "The request conflicts with existing data." rather than naming the code.
- Ledger partitions exist only for the month V10 ran in and the next two; later rows go to `inventory_txn_default`. There is no job that creates future partitions, and once the default partition holds rows for a month, creating that month's partition fails until those rows are moved out.
- `processed_requests` grows without limit; nothing deletes old keys.
- Idempotency keys are global and are not tied to the request: reusing a key on a different record or endpoint returns that record's current state and changes nothing. A repeat returns the current state, not the original response (the table stores no response).
- An outbound shipment's reservation row is still found by "lowest inventory id for the item in the warehouse" at process, ship and cancel time. Phase D added allocations for orders only; shipments do not use them. If that row changes in between (deleted, or a lower-id row appears), ship or cancel can hit the wrong row and return 409. Phase D's `allocations.inventory_id` replaces this.
- Seeded shipment 1 (PROCESSING) has no SHIPMENT-tagged ALLOCATE in the ledger; its reservation is part of item 1's opening balance. Shipping it works and reconciles.
- `PATCH /inventory/{id}/reserve` with `quantity` of zero or below now returns 400 ("Quantity must be positive"); before Phase C a negative value silently reduced the reservation and zero was a no-op.
- Rows created by receiving get the column default `reorder_point` of 10, so a small receipt shows up in `/inventory/low-stock`.
- "Warehouse has no active RECEIVING location" reuses `InvalidStatusTransitionException` for its 409.
- `PUT /inventory/{id}` can still change a row's zone without a ledger entry (zone is not a ledger dimension; location is).
- Under contention, `SKIP LOCKED` allocation leaves orders SHORT while stock is still free (measured: 20 concurrent orders of 3 against three bins of 10 gave 6 ALLOCATED and 14 SHORT, 18 of 30 units allocated). Retrying SHORT orders fills the rest. Nothing retries them automatically yet.
- An inventory row that has ever had an allocation cannot be deleted (`allocations.inventory_id` is RESTRICT, and cancelled and picked allocations stay as history); `DELETE /api/v1/inventory/{id}` returns 409 for it.
- An item that appears on any order line cannot be deleted (`outbound_lines.item_id` is RESTRICT).
- A duplicate `externalOrderId` returns the stored order even if the new payload differs; nothing compares them.
- Orders and allocations are not tied to shipments; the two outbound paths exist side by side, as the plan requires.
- Picked stock sits at the pack location as reserved quantity that no OPEN allocation covers (the allocation is PICKED and still points at the source row). Nothing ships it yet; a later packing and shipping step needs to consume that row.
- `/tasks/next` hands out PICK tasks only. COUNT tasks created by short picks stay READY because no endpoint confirms them yet, and PUTAWAY, REPLEN and MOVE tasks are never created.
- A short pick writes the missing units off immediately (ADJUST_OUT, reason `SHORT_PICK`) instead of waiting for the count, and re-allocation may pick the same bin again if it still shows other free stock.
- An order whose short line could not be re-allocated still becomes PICKED; only `qtyPicked < qtyOrdered` on the line shows the gap, and nothing reports it.
- `X-User-Id` is trusted as given; anyone can claim or confirm as any user until authentication exists. A claimed task that is never confirmed stays CLAIMED forever (no timeout or unclaim).
- Release rejects a warehouse with no active PACK location with 409, reusing `InvalidStatusTransitionException`, like receiving does for RECEIVING.
- Removing `SKIP LOCKED` from the claim query does not make `TaskConcurrencyTest` fail: Postgres re-checks a row that was locked and skips it if it is no longer READY, so claims stay distinct and only serialize. The test proves correctness, not the absence of waiting. Removing the row lock entirely makes it fail (5 distinct tasks for 20 callers).
- `OutboundOrder`, `OutboundLine` and `Allocation` use Lombok `@Getter`/`@Setter` rather than `@Data`, because the order and its lines refer to each other and `@Data`'s `hashCode`/`toString` would recurse.
- Several integration tests (`InventoryConcurrencyTest`, `ShipmentWorkflowTest`) still insert inventory rows with JDBC, bypassing the ledger, and delete their ledger rows by item afterwards. That is test-only, but it means those rows never reconcile while the test runs.
- On JDK 25, Lombok (`lombok.permit.Permit`, at compile time) and ModelMapper 3.2.4 (`TypeResolver`, at runtime) call deprecated `sun.misc.Unsafe` methods and print warnings. Neither breaks anything yet. ModelMapper 3.2.8 (Phase 2) removed its warning; the Lombok one (still present with 1.18.48) needs an upstream fix.
- With Jackson 3, `/actuator/health` orders its keys differently (`components` before `status`). Our own endpoints' JSON is byte-identical apart from timestamps. Nothing known depends on key order; the compose healthcheck uses `pg_isready`.
- The old dev database password (and pgAdmin `admin`/`admin`) remain in public git history. The user decided against rewriting history; rotating the password makes the old value useless. Until rotated, the running stack still uses the old value from the local `.env`.
